# backend-guardrails

리뷰어 경험에 의존하던 백엔드 규칙을 **시스템이 막게** 만드는 실험.

목표는 "개발 규칙 문서"가 아니라 **위반하면 merge 할 수 없는 규칙**이다.

---

## 왜 탐지율만으로는 부족한가

**모든 걸 잡는 규칙은 탐지율 100% 지만 쓸모없다. 팀이 바로 꺼버린다.**

그래서 검증을 세 층으로 나눈다.

| 층 | 묻는 것 | 없으면 |
|---|---|---|
| ① 탐지 | 위반을 잡는가 | 규칙이 무의미 |
| ② **오탐** | **멀쩡한 코드를 안 잡는가** | **팀이 규칙을 끈다** |
| ③ 차단 | CI 에서 실제로 merge 를 막는가 | 문서일 뿐 |

②를 재려면 **위반처럼 보이지만 정상인 경계 사례**가 필요하다.
`bad/` 는 쉽고 **`good/` 이 어렵다.** 거기가 이 프로젝트의 난이도 전부다.

그리고 ArchUnit 규칙은 **통과만 하면 죽어 있어도 모른다.**
조건을 잘못 고쳐 아무것도 안 잡게 돼도 CI 는 초록불이다.
그래서 **규칙을 테스트하는 테스트**를 따로 둔다 — 규칙 하나당 둘.

```java
@Test void R3_규칙은_위반_fixture에서_반드시_실패한다() { ... }
@Test void R3_규칙은_정상_fixture를_통과시킨다()      { ... }
```

## 규칙 10개 — 자동 검증 가능 여부

| # | 규칙 | 자동 검증 |
|---|---|---|
| R1 | Controller 에 `@Transactional` 금지 | ✅ |
| R2 | 조회 전용 메서드는 `readOnly = true` | ⚠️ 부분 |
| R3 | 트랜잭션 안에서 외부 시스템 호출 금지 | ✅ |
| R4 | `@Transactional` 은 `public` 에만 | ✅ |
| R5 | self-invocation 으로 트랜잭션 기대 금지 | ⚠️ 어려움 |
| R6 | Repository 는 Service 에서만 호출 | ✅ |
| R7 | 트랜잭션 안에서 블로킹 대기 금지 | ✅ |
| R8 | 반복문 안 단건 저장/조회 금지 | ❌ → B-M4 |
| R9 | 락을 잡는 쓰기와 무거운 작업을 분리 | ⚠️ 어려움 |
| R10 | 외부 알림 발송은 커밋 이후 | ✅ 부분 |

**자동 5.5 / 반자동 3 / 불가 1.5.**
이 구분 자체가 결과물이다 — *"규칙 10개를 만들었다"* 보다
**"10개 중 무엇을 기계가 막을 수 있는지 갈랐다"** 가 더 정확하다.

⚠️ 로 판정한 규칙은 **오탐률을 재기 전까지 차단이 아니라 경고**로 둔다.

## R9·R10 의 출처

두 규칙은 실제 장애의 사후 검증에서 나왔다 —
공지 푸시 배치가 콘텐츠 행을 **99초** 점유해 상세 페이지가 죽은 사건이다.

재현 실험에서 완료 표시를 건별 커밋으로 바꾸자
조회 실패 3건 → **0건**, 조회 처리량 882 → **2,377건**(2.7배).
