# 트랜잭션 규칙 10 (B-M1)

> 리뷰어 경험에 의존하던 규칙을 **시스템이 막게** 만드는 것이 목표다.
> 그래서 각 규칙에 **자동 검증 가능 여부**를 먼저 판정한다. 못 막는 규칙은 못 막는다고 적는다.

## 판정 요약

| # | 규칙 | 자동 검증 | 근거 출처 |
|---|---|---|---|
| R1 | Controller 에 `@Transactional` 금지 | ✅ ArchUnit | 일반 |
| R2 | 조회 전용 메서드는 `readOnly = true` | ⚠️ 부분 | 일반 |
| R3 | 트랜잭션 안에서 외부 시스템 호출 금지 | ✅ ArchUnit | 일반 |
| R4 | `@Transactional` 은 `public` 에만 | ✅ ArchUnit | 프록시 |
| R5 | self-invocation 으로 트랜잭션 기대 금지 | ⚠️ 어려움 | 프록시 |
| R6 | Repository 는 Service 에서만 호출 | ✅ ArchUnit | 계층 |
| R7 | 트랜잭션 안에서 블로킹 대기 금지 | ✅ ArchUnit | 락 |
| R8 | 반복문 안 단건 저장/조회 금지 | ❌ 정적 불가 → B-M4 | N+1 |
| R9 | 락을 잡는 쓰기를 무거운 작업과 같은 트랜잭션에 두지 않기 | ⚠️ 어려움 | **장애 A** |
| R10 | 외부 알림 발송은 커밋 이후 | ✅ ArchUnit(부분) | **장애 A** |

**자동 5.5 / 반자동 3 / 불가 1.5.** 이 구분 자체가 결과물이다 —
"규칙 10개를 만들었다"보다 **"10개 중 무엇을 기계가 막을 수 있는지 갈랐다"** 가 더 정확하다.

> **장애 A** = 공지 푸시 배치가 콘텐츠 행을 99초 점유해 상세 페이지가 죽은 사건.
> R9·R10 은 그 사후 검증에서 나온 규칙이다.

## R1. Controller 에 `@Transactional` 금지

**왜** — Controller 트랜잭션은 요청 전체를 감싼다. 뷰 렌더링·직렬화·외부 호출까지 트랜잭션 안에
들어가 커넥션을 오래 문다. 트랜잭션 경계는 유스케이스 단위여야 한다.

```java
// ❌ 위반
@RestController
class OrderController {
    @Transactional                       // 요청 전체가 한 트랜잭션
    @PostMapping("/orders")
    public OrderResponse create(...) { ... }
}

// ✅ 정상
@RestController
class OrderController {
    @PostMapping("/orders")
    public OrderResponse create(...) {
        return orderService.create(...);  // 트랜잭션은 서비스가 연다
    }
}
```

**자동 검증** ✅ — `@Controller`/`@RestController` 가 붙은 클래스와 그 메서드에 `@Transactional` 이 없어야 한다.

---

## R2. 조회 전용 메서드는 `@Transactional(readOnly = true)`

**왜** — `readOnly` 는 플러시를 끄고(Hibernate `FlushMode.MANUAL`) 더티체킹 스냅샷을 만들지 않는다.
읽기 전용 복제본 라우팅의 근거로도 쓰인다.

```java
// ❌ 위반
@Transactional
public List<Order> findAll() { return repo.findAll(); }

// ✅ 정상
@Transactional(readOnly = true)
public List<Order> findAll() { return repo.findAll(); }
```

**자동 검증** ⚠️ **부분** — 메서드 이름(`find*`, `get*`, `search*`)으로 판정하면
**오탐이 난다.** `getOrCreate()` 처럼 이름은 조회인데 쓰기인 메서드가 있다.

→ **이름 규칙 + 리포지토리 쓰기 메서드 호출 여부**를 함께 본다.
쓰기 호출이 없으면서 `readOnly` 가 아닌 경우만 잡는다. 그래도 남는 오탐은 `good/` fixture 로 잰다.

---

## R3. 트랜잭션 안에서 외부 시스템 호출 금지

**왜** — HTTP·메시지 발행·파일 IO 는 응답 시간이 통제 밖이다.
그동안 트랜잭션이 열려 있으면 **락과 커넥션을 남이 정한 시간만큼 붙잡는다.**

```java
// ❌ 위반
@Transactional
public void place(Order order) {
    repo.save(order);
    paymentClient.charge(order);         // 외부 API — 응답까지 트랜잭션이 열려 있다
}

// ✅ 정상
public void place(Order order) {
    orderService.saveInTx(order);        // 트랜잭션은 여기서 닫는다
    paymentClient.charge(order);         // 커밋 후 호출
}
```

**자동 검증** ✅ — `@Transactional` 메서드에서 외부 클라이언트 타입
(`RestClient`, `WebClient`, `RabbitTemplate`, `KafkaTemplate` 등)을 호출하지 않아야 한다.

---

## R4. `@Transactional` 은 `public` 메서드에만

**왜** — Spring AOP 프록시는 **바깥에서 들어오는 호출**만 가로챈다.
`private`/`protected` 에 붙이면 **애노테이션이 조용히 무시된다.** 트랜잭션이 없는데 있다고 믿게 된다.

```java
// ❌ 위반 — 애노테이션이 아무 일도 하지 않는다
@Transactional
private void updateInternal(Order o) { ... }

// ✅ 정상
@Transactional
public void update(Order o) { ... }
```

**자동 검증** ✅ — `@Transactional` 이 붙은 메서드는 `public` 이어야 한다.

---

## R5. self-invocation 으로 트랜잭션 기대 금지

**왜** — R4 와 같은 이유다. 같은 클래스 안에서 `this.method()` 를 부르면 **프록시를 안 거친다.**

```java
// ❌ 위반 — save() 의 @Transactional 이 적용되지 않는다
@Service
class OrderService {
    public void process(Order o) {
        save(o);                          // this.save() — 프록시 통과 안 함
    }
    @Transactional
    public void save(Order o) { ... }
}

// ✅ 정상 — 트랜잭션 경계를 별도 빈으로 분리
@Service
class OrderService {
    private final OrderTxService tx;
    public void process(Order o) { tx.save(o); }
}
```

**자동 검증** ⚠️ **어려움** — 호출 그래프를 따라가야 한다.
ArchUnit 으로 *"같은 클래스의 `@Transactional` 메서드를 직접 호출하는 메서드"* 는 잡을 수 있으나
**정상 케이스(트랜잭션 안에서 같은 클래스 헬퍼 호출)와 구분이 안 된다.**

→ **차단이 아니라 경고**로 둔다. 오탐률을 재고 나서 판단한다.

---

## R6. Repository 는 Service 에서만 호출

**왜** — Controller 가 Repository 를 직접 부르면 트랜잭션 경계와 도메인 규칙이 우회된다.
계층이 무너지면 R1·R3 도 같이 무너진다.

```java
// ❌ 위반
@RestController
class OrderController {
    private final OrderRepository repo;   // Controller → Repository
}
```

**자동 검증** ✅ — ArchUnit 계층 규칙(`layeredArchitecture`).

---

## R7. 트랜잭션 안에서 블로킹 대기 금지

**왜** — `Thread.sleep`, 동기 `Future.get()`, 재시도 백오프 대기가 트랜잭션 안에 있으면
**락을 쥔 채로 잠든다.** R3 의 일반화다.

```java
// ❌ 위반
@Transactional
public void retryUpdate(Long id) {
    repo.update(id);
    Thread.sleep(1000);                   // 락을 쥔 채 1초
}
```

**자동 검증** ✅ — `@Transactional` 메서드에서 `Thread.sleep`, `Future.get`,
`CountDownLatch.await` 등을 호출하지 않아야 한다.

---

## R8. 반복문 안에서 단건 저장/조회 금지

**왜** — N+1. 100건이면 쿼리 100번이고, 그만큼 트랜잭션이 길어진다.

**자동 검증** ❌ **정적 분석으로는 불가** — 반복문 안의 호출을 바이트코드에서 판정하기 어렵고,
반복 횟수를 모른다.

→ **B-M4 Query Count Test 로 넘긴다.** 런타임에 실행된 쿼리 수를 세는 것이 정확하다.

---

## R9. 락을 잡는 쓰기를 무거운 작업과 같은 트랜잭션에 두지 않기

**왜** — **장애 A 에서 나온 규칙이다.**
배치가 콘텐츠 3건을 한 트랜잭션으로 돌면서, 첫 건의 완료 표시(`UPDATE`, 수 ms)를
나머지 두 건의 발송(각 60~70초)까지 끝난 뒤에야 커밋했다. **그 행이 99초 잠겼다.**

```java
// ❌ 위반
@Transactional
public void publishAll(List<Content> contents) {
    for (Content c : contents) {
        push.send(c);                     // 무겁다 (수십 초)
        repo.markDone(c);                 // 락을 잡는다 (수 ms)
    }
}                                         // 커밋은 마지막에 — 첫 건이 가장 오래 잠긴다

// ✅ 정상 — 락을 잡는 쓰기만 건별로 끊는다
public void publishAll(List<Content> contents) {
    for (Content c : contents) {
        push.send(c);
        markDoneService.markDoneInNewTx(c);   // REQUIRES_NEW — 즉시 커밋
    }
}
```

**재현 실험 결과** — 완료 표시를 건별 커밋으로 바꾸자 조회 실패 3건 → **0건**,
조회 처리량 882 → **2,377건**(2.7배). 3회 반복 동일.

**핵심** — 커밋 비용은 **건수**에 비례하고, 락 손실은 **트랜잭션 길이**에 비례한다. 다른 축이다.

**자동 검증** ⚠️ **어려움** — "무겁다"를 정적으로 판정할 수 없다.
→ *"반복문 안에서 외부 호출과 리포지토리 쓰기가 같은 트랜잭션에 있는 경우"* 로 좁혀 **경고**로 둔다.

## R10. 외부 알림 발송은 커밋 이후

**왜** — **장애 A 에서 나온 규칙이다.**
푸시를 받은 사람은 20~90초 안에 그 콘텐츠를 연다.
**푸시가 나간 뒤에도 락이 잡혀 있으면, 배치가 자기가 잠근 행에 부딪힐 트래픽을 스스로 예약하는 셈이다.**

```java
// ❌ 위반
@Transactional
public void publish(Content c) {
    repo.markDone(c);
    push.sendAll(c);                      // 커밋 전에 푸시가 나간다
}

// ✅ 정상
public void publish(Content c) {
    contentService.markDoneInTx(c);       // 먼저 커밋
    push.sendAll(c);                      // 도달 시점에 락은 이미 풀려 있다
}
```

> 부수 효과 하나 — 커밋 전에 발송하면 롤백 시 **발송만 나가고 기록이 취소**된다.
> 다음 실행이 같은 대상에 또 보낸다. 순서를 뒤집으면 그 위험도 줄어든다.

**자동 검증** ✅ **부분** — `@Transactional` 메서드에서 알림 발송 타입을 호출하지 않아야 한다.
R3 의 특수화라 같은 규칙으로 잡히는 부분이 있다.
